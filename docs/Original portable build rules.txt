PORTABLE BUILD RULES (for any game built with AI helpers)

1. THE FOLDER (on the Desktop)
  START HERE.txt   what each folder is, in one line each. Keep it current.
  vX\              the newest playable version only (old ones removed after asking).
  docs\            the text files below.
  maps\            one short map per system, plus PROJECT MAP.txt.
  tests\           helper test notes.
  toolchain\       the build tools kit, if the workspace can't download them.
  work\            helpers' working copies. Use git worktrees, not full copies. Clear old ones each version.

2. THE TEXT FILES TO KEEP UP (in the repo, copied to the Desktop each version)
  CLAUDE.md        the rules: owner's standing rules (quoted), how to build, test, release, who does what.
  CODE MAP.md      where every system lives, a few lines each.
  maps/*.txt       one per system, under 80 lines: its files, main types and methods with file:line, what it reads and writes, its tests. Every name in a map must exist in the code (grep it).
  PROJECT MAP.txt  generated by a script: folder and file sizes, big files flagged. Regenerate after changes.
  ROADMAP.md       current stage only, with the owner's requests quoted. Older plans go to docs/roadmap/.
  briefs/          the written brief for each helper job; good ones get reused.

3. THE RUNNING RECORDS: what each holds, when it changes, how it stays short
  VERSION MAP.txt  the plan ahead: stages, each a few versions, one line per version ("v0.4.2 The well: dig, draw, it can run dry"), marked done / doing / next. Update when a version ships or the owner changes the plan. Done stages shrink to one line.
  DEV LOG.txt      newest first, one entry per work session or version: date, what was done, what broke and why, decisions made (and who made them), what's next. 5 to 10 lines an entry. Past about 40 KB, move old entries to docs/archive/DEV LOG <years>.txt.
  CHANGES vX.md    release notes for one version, for the owner: their request quoted, what changed in play, mistakes found, tests run. Written at release; never edited after.
  HANDOFF.md       the state right now, for the next session: what works, what's half done, where, and the next step. Rewritten (not appended) at the end of each session. Under 30 KB.
  TO BE TESTED.md  things only playing can check, by version. Lines are removed once checked.
  VERSIONS.md      one line per version: number, commit, date. Appended at release.
  Rule: a record that only grows gets archived; a record of "now" gets rewritten.

4. READ ORDER for a new session or helper
  PROJECT MAP, then HANDOFF, then CODE MAP, then the maps of the systems in the task. Then the newest DEV LOG entry. Then grep. Never read a file over 40 KB whole; read it in parts. A brief names the maps to read, not whole files.

5. SIZE LIMITS
  Code files: split past about 60 KB into parts named after the class plus the part (partial classes).
  Docs: past about 80 KB, move old sections to an archive folder, word for word, with an index.
  Logs and test output stay out of the repo.
  Check after any split that no line was lost (a small script comparing lines before and after).

6. VERSIONS AND DELIVERY
  One playable step per version. Bump the version string, write CHANGES, update the docs, commit, tag. Build the release in a separate worktree. Deliver to the Desktop: the vX folder plus a shortcut with the game's icon, and the changed docs and maps. Push main to GitHub when the version is done. A version that changes nothing in play is still a version.

7. TESTING
  Every test run under 3 minutes, aim for under 1. Build dev tools that answer a question fast instead of running long simulations. Group tests that can share a setup into blocks. Each version runs the tests of what it touched; full rounds only at milestones. Never skip or weaken a test to get green; fix the cause or show why the check was wrong.

8. WHO DOES WHAT
  The lead (strongest model) plans, designs, balances systems, talks to the owner, reviews, merges, releases.
  Builders (mid model) do work from a written brief in their own worktree.
  Clerks (small model) run tests and pull out results; they don't diagnose.
  Experts (strongest model, high effort) do hard problems and independent checks of risky changes.
  Delegate when the job can be briefed, checked by a build or test, needs no taste or cross-system balance, and is worth more than 15 minutes of the lead's time. The lead reads every helper's whole diff, builds it and runs its tests before merging. Helpers never delete files; only the lead does, after asking the owner. A brief gives: the goal, files to read, files it may change, names to keep, rules, how to build and test, what done means, what to report.

9. HABITS
  Keep working when the owner writes mid-task. Tell the owner plainly about mistakes, including your own. Plain English in docs and game text: short sentences, no jargon. Never kill processes by name pattern; only by explicit process id. Never run two game instances at once. Never commit everything blindly; add files by name. Don't poll in short sleeps; start long runs in the background and check back once.
