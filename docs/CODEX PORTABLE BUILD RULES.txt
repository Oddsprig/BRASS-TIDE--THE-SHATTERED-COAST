PORTABLE GAME BUILD RULES — CHATGPT / CODEX WORKFLOW

Adapted from the owner's portable build rules, 20 October 2026.
The working folders fit Codex and its tools. The build, review, record-keeping, testing and delivery rules carry over.

1. LOCATIONS
  The attached project/workspace is the source of truth; its Git root holds the source and project records.
  work/ holds scratch analysis, helper Git worktrees, logs, test output and a separate release worktree. Keep generated noise out of the repo.
  outputs/ holds user-facing portable releases, release archives, reports and final documents. Use absolute clickable links in chat.
  A release folder contains only the current playable version, START HERE.txt, docs/, maps/, tests/ notes and the launcher/icon. Old releases are removed only after asking.
  toolchain/ holds portable build tools only when existing tools or downloads cannot supply them. Never make the released game depend on an editor or a developer's absolute path.
  Desktop delivery is an explicit extra destination. Prepare the complete release first; request only the filesystem access needed to place the folder and launcher. Never claim a Desktop copy or shortcut exists until verified.

2. PERSISTENT RULES AND MAPS
  AGENTS.md replaces CLAUDE.md as the main Codex instruction file. Quote the owner's standing rules and record build, test, release, roles and paths. A CLAUDE.md compatibility pointer is optional if another tool needs it; do not duplicate rules that can drift.
  CODE MAP.md: where each system lives, a few lines each.
  maps/<system>.txt: one map per system, under 80 lines: files, real types and methods with file:line, reads/writes and tests. Verify every named symbol with rg.
  maps/PROJECT MAP.txt: generated by a checked-in script; folder/file sizes and large-file flags. Regenerate after changes.
  ROADMAP.md: the current stage only, with the owner's requests quoted. Move older plans into docs/roadmap/.
  briefs/: one written brief per helper job. Reuse good briefs.

3. RUNNING RECORDS
  VERSION MAP.txt: stages ahead, a few versions each, one line per version, marked done/doing/next. Completed stages shrink to one line. Update when a version ships or scope changes.
  DEV LOG.txt: newest first; 5–10 lines per session/version with date, work, causes of failures, decisions and decision-maker, next step. Archive old entries verbatim around 40 KB into docs/archive/.
  CHANGES vX.md: immutable release notes written at release: owner request quoted, changes in play, mistakes found and tests run.
  HANDOFF.md: replace with the current state at session end; works, incomplete work, locations, next step and any approval still required. Under 30 KB.
  TO BE TESTED.md: play-only questions by version. Remove checked items after recording results in test notes.
  VERSIONS.md: append version, exact commit, date and release location after shipping.
  Records of now are rewritten. Records of history are archived rather than allowed to grow forever.

4. READ ORDER
  AGENTS.md applies first. Then read PROJECT MAP, HANDOFF, CODE MAP, only assigned system maps and the newest DEV LOG entry. Search exact symbols with rg next.
  Read files over 40 KB in relevant chunks. A brief points to maps and precise code inputs, not a whole repository. Missing bootstrap records must be created honestly.

5. SIZE AND SOURCE HYGIENE
  Split code near 60 KB into logical files. Use partial classes only in languages that support them.
  Archive documentation near 80 KB, preserving old text and an index. For mechanical splits, compare before/after lines so none are lost.
  Logs, screenshots used only for testing, cache folders, credentials and test output stay outside the repo. Final evidence belongs in the release only when useful.

6. VERSIONS AND DELIVERY
  One playable step per version. For Brass Tide use an integer build counter: 1 displays 0.001; 2 displays 0.002. Advance by exactly 0.001 each release.
  Bump version, write CHANGES, update maps/records, commit named files and tag. Build/export from a separate Git worktree of the release commit.
  Verify the portable game starts without the engine editor or developer tools. Deliver its folder plus original launcher icon and current docs/maps. Keep the playable build, launcher and records consistent.
  Push main and the release tag to the verified intended GitHub repository when authorized and accessible. A missing repository/account permission is reported precisely, not bypassed by choosing an unrelated repository.

7. TESTS
  Each test run under 3 minutes; aim under 1. Build short tools that answer a specific question. Share setup in blocks.
  Test touched systems each version; full rounds at milestones. Never skip/weaken tests for a green result; fix the cause or show why the check was wrong.
  Separately record automated tests, visual inspection and actual playtests. A successful compile alone is not a successful playtest. Report performance as measured, with its scenario and limits.

8. TEAM AND APP TOOLS
  The Codex lead owns architecture, taste, cross-system balance, user updates, complete diff review, independent tests, merge and release.
  Use app-native subagent tools for authorized specialists; use the requested connected helper service for other authorized helpers. Do not create sidebar chats unless the user asks for new chats. Do not silently change requested models or helper count.
  Builders work from written briefs in their own Git worktrees. Clerks can run checks and extract results; experts handle hard problems and independent risky-change review.
  Delegate a bounded job when its brief is clear, build/test can verify it, it needs no lead taste/cross-system judgment, and it saves meaningful time.
  Each brief states goal, maps/inputs, allowed files, names to keep, rules, build/tests, done condition and report. Helpers never delete files or spawn extra helpers without authorization.
  Lead reads the full diff and runs its build/tests before integration. Preserve helper reports exactly; add a separate verdict and evidence.
  Use purpose-built app tools and official documentation when needed. Keep credentials in supported secure flows, never source/logs/chat. Sandbox permission requests name only the needed paths/network access and are made after useful authorized preparation.

9. HABITS
  Keep working while the owner sends steering; incorporate it into the active goal. Plain English in game text, docs and updates. State mistakes plainly.
  Never kill processes by pattern; use an owned explicit PID. Never run two game instances. Add files to Git by name.
  Start long work in retained/background sessions; avoid busy polling. Give meaningful updates about once per minute. Preserve state across context compaction using HANDOFF and the records.
  Ask before deletion, discarding old releases or genuinely irreversible actions. Existing authorization carries forward; routine reversible implementation does not need repeated permission.
