PUBLIC API (game/scripts/coastal_stories.gd, all static)
- ensure(state) -> Dictionary: state["stories"] = {catalog (copied from
  res://data/coastal_stories.json, read once), chains {chainId: {stage,
  flags[], leads[], done, startedDay}}, events[] (<=128 settled
  "story:<chain>:<stage>:<choice>" ids), consequences[] (<=64 pending
  records), notified[]}. Progress naming unknown chains/stages is dropped.
- available(core) -> Array: unstarted chains whose startPort is the current
  harbor and whose startContact is already met (Contacts visit), each with
  first-stage nextAction, journal location and choices. No writes beyond
  ensure()/Contacts.ensure().
- choose(core, chain_id, choice_id) -> Dictionary: starts the chain at its
  harbor when needed (the start record persists even if stage one's gate is
  elsewhere), then settles one decision. Unknown chain/choice, finished
  chain, already-recorded event id, missing requiresFlag, unmet gate and
  unaffordable delivery cost all refuse BEFORE any write (atomic; the
  destination stage is also validated before cargo moves). On success:
  optional delivery transfers player cargo -> named port stocks, flags and
  site leads are recorded, an optional "reveal" legitimately sights a site
  through Exploration.discover_near, faction/contact consequences are
  appended as pending {id,kind,target,amount,reason,day,applied:false}
  records for ROOT to apply, and the chain advances or finishes. Returns
  ok/message plus chainId, stage, done, eventId, consequences, leads.
- journal(state) -> Array: one entry per started chain {chainId,title,
  approach,stage,stageTitle,done,nextAction,location {kind,id,name,x,y},
  flags,leads,choices}; location resolves to the gated site coordinates or
  the named/start port from state.ports.
- tick(core) -> Array: emits each active stage's "gate_ready" notice once
  when its gate first becomes satisfiable; never advances a chain itself.
Gate types in data: site {site,level} (Exploration levels 1 sighted /
2 charted / 3 surveyed), at_port {port}, visit {port} (a dated Contacts
market snapshot exists), npc_defeated {owner} (fleetOwner inactive or all
boats sunk), contact_met {contact}, none. Choice fields: id,text,next
(stage id or "done"),tradeoff,requiresFlag?,setFlags[],cost? {good,qty,
port},leads[],reveal?,consequences[] {kind faction|contact,target,amount,
reason}. Arbitrary JSON cannot mint anything: unknown consequence kinds are
dropped, costs only move existing cargo into existing port stocks, and no
choice field can create coins, boats, crew or goods. NO chain uses coins
or escrow at all, so Money.total needs no story term.

CAVEATS / KNOWN SHORTCOMINGS
- Consequence amounts are first-pass relationship tuning for root's
  factions/contacts scales; they do nothing until root applies them.
- "visit" gates trust Contacts snapshots, so a captain who docks without
  root calling Contacts.visit (once integrated at arrival) would not pass;
  that coupling is deliberate and documented above.
- Chains are linear stage lists with flag-gated branches, not a general
  graph engine; that covers these four stories without inventing a quest
  scripting language root must then secure.
- tick() notices are keyed by chain+stage, so re-entering a stage id (not
  possible in the authored linear chains) would not re-notify.
